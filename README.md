# ЧАСТЬ I: БЭКЕНД-ИНФРАСТРУКТУРА (NODE.JS + EXPRESS + POSTGRESQL + REDIS)

## 1. Системная архитектура бэкенда

### 1.1 Сетевая инфраструктура и деплой
*   **Nginx Proxy Manager (NPM):** 
    *   Принимает защищенный трафик на порту `443` (HTTPS) с сертификатами Let's Encrypt и пересылает его на локальный порт контейнера Node.js (`8080`).
    *   **Websockets Support:** Включено проксирование заголовков `Upgrade` и `Connection` для бесперебойной работы протокола Wisp (сетевой транспорт Scramjet) [2] и чат-вебсокетов.
    *   **Безопасность заголовков:** Настройка HSTS, блокировка Clickjacking (`X-Frame-Options: SAMEORIGIN`) и строгая политика CORS.
*   **Системный DNS-AdBlock (VPS):** На уровне `/etc/resolv.conf` провайдера VPS прописаны адреса **AdGuard DNS** (`94.140.14.14`, `94.140.15.15`) [3.5]. Это гарантирует автоматическую фильтрацию и блокировку трекеров, метрик (Яндекс, Google) и рекламных скриптов еще до того, как они дойдут до браузеров пользователей [3.5].

### 1.2 Архитектура бэкенда (Node.js / Express)
*   **Wisp & Libcurl WASM Transport:** Сервер интегрирован с `wisp-server-node` (или `wisp-js/server`) [1.4.9, 8.1.3]. Обрабатывает входящие бинарные TCP/UDP потоки через WebSockets, транслируемые сетевой WASM-библиотекой `libcurl` из браузеров пользователей [2, 8.1.3].
*   **Работа с СУБД:** В качестве базы данных используется **PostgreSQL** в связке с асинхронным ORM/Query Builder (например, Prisma или TypeORM) с поддержкой пула подключений.
*   **Redis-слой:** Используется для:
    *   *Rate Limiting (Лимитирование запросов):* Защита эндпоинта авторизации и отправки сообщений в чат от спама по алгоритму Token Bucket.
    *   *WebSocket Session Store:* Отслеживание активных подключений пользователей в реальном времени.

### 1.3 Спецификация безопасности API и авторизация (JWT + Rolling HttpOnly Cookie)
*   **Двухтокенная авторизация (JWT):**
    *   **Access Token:** Краткосрочный (15 минут), хранится исключительно в оперативной памяти Vue 3 (Pinia) и прикрепляется к заголовкам запросов к API. При закрытии вкладки стирается.
    *   **Refresh Token:** Долгосрочный (7 дней), записывается сервером в виде куки с флагами `HttpOnly`, `Secure` и `SameSite=Strict`. JS-код не имеет к нему доступа, что исключает кражу через XSS.
*   **Механизм Rolling Refresh:** При обновлении токена через `/api/auth/refresh` старый Refresh-токен инвалидируется, а пользователю выдается пара новых токенов, продлевая сессию еще на 7 дней (скользящая сессия).
*   **Хеширование паролей (Argon2id):** Все пароли пользователей, сгенерированные Telegram-ботом, хешируются на бэкенде с помощью алгоритма Argon2id перед записью в PostgreSQL [1]. Прямое хранение паролей исключено [1].

## 2. Концептуальная схема Базы Данных (PostgreSQL)

```
                       +-------------------+
                       |       users       |
                       +-------------------+
                       | id (UUID, PK)     |<---+
                       | username (VARCHAR)|    |
                       | password_hash(STR)|    |
                       | is_active (BOOL)  |    |
                       +-------------------+    |
                                 |              |
         +-----------------------+              |
         |                       |              |
         v                       v              |
+-------------------+  +-------------------+    |
|   sessions_sync   |  |   chat_messages   |    |
+-------------------+  +-------------------+    |
| user_id (UUID, FK)|  | id (SERIAL, PK)   |    |
| encrypted_cookies |  | sender_id (FK)    |----+
| open_tabs (JSONB) |  | recipient_id (FK) |----+ (nullable)
| updated_at (TIME) |  | encrypted_text    |
+-------------------+  | iv (VARCHAR)      |
                       | created_at (TIME) |
                       +-------------------+
```

### 2.1 Таблица `users` (Учетные записи)
*   `id` (UUID, primary key) — Уникальный криптостойкий идентификатор пользователя (UUIDv4).
*   `username` (String, unique, indexed) — Логин, сгенерированный Telegram-ботом.
*   `password_hash` (String) — Хэш пароля (Argon2id) [1].
*   `is_active` (Boolean) — Флаг блокировки аккаунта.

### 2.2 Таблица `sessions_sync` (Zero-Knowledge синхронизация кук)
*   `user_id` (UUID, foreign key, indexed) — Связь с таблицей `users`.
*   `encrypted_cookies` (Text, nullable) — Огромный зашифрованный на клиенте (через AES-GCM-256) текстовый блок (blob/payload), содержащий всю локальную базу данных IndexedDB/cookies проксируемых сайтов [1]. Сервер видит только нечитаемые кракозябры [1].
*   `open_tabs` (JSONB) — Список открытых на момент закрытия вкладок (зашифрованный JSON), необходимый для автоматического восстановления сессии при повторном входе.
*   `updated_at` (DateTime) — Время последней синхронизации.

### 2.3 Таблица `chat_messages` (Зашифрованный чат)
*   `id` (Integer, primary key) — Идентификатор сообщения.
*   `sender_id` (UUID, foreign key) — Идентификатор отправителя.
*   `recipient_id` (UUID, foreign key, nullable) — Идентификатор получателя. Если `null` — сообщение отправлено в общий (глобальный) чат.
*   `encrypted_text` (Text) — Зашифрованный текст сообщения (AES-GCM-256) [1]. Дешифрация происходит исключительно на клиентах получателей.
*   `iv` (String) — Вектор инициализации (Initialization Vector), необходимый для расшифровки алгоритмом AES-GCM.
*   `created_at` (DateTime, indexed) — Время отправки сообщения.

## 3. Интеграция с Telegram-ботом (Python / Requests)

*   **Роль бота:** Генератор учетных данных и шлюз авторизации.
*   **Логика взаимодействия:**
    1. Пользователь запускает бота в Telegram (`/start`).
    2. Бот генерирует случайный уникальный логин (например, `user_4829`) и надежный пароль из 12 символов.
    3. Бот отправляет POST-запрос на бэкенд `/api/auth/register` с логином и хэшем пароля, используя защищенный API-токен в заголовках.
    4. Бэкенд фиксирует пользователя в PostgreSQL.
    5. Бот выводит пользователю в Telegram его логин, пароль и ссылку на ваш домен `https://web.chabupelik.su/`.

# ЧАСТЬ II: ФРОНТЕНД-ИНФРАСТРУКТУРА (VUE 3 + VITE + SCRAMJET)

## 1. Системная архитектура клиентской части (SPA)

### 1.1 Стек технологий и сборка
*   **Vue 3 (Composition API):** Логика вкладок и шифрования вынесена в реактивные хуки (composables).
*   **Pinia:** Хранение токенов в оперативной памяти и текущего состояния активного таба.
*   **Vite:** Высокоскоростной сборщик проекта.
*   **Scramjet & Bare-Mux (libcurl WASM):** Встроенный в проект сетевой стек для перехвата трафика на лету [8.1.3].

### 1.2 Архитектура безопасности Zero-Knowledge (Шифрование сессии)
Бэкенд никогда не видит пароли и куки в открытом виде [1]. Дешифрация и шифрование происходят на стороне клиента с помощью **Web Crypto API** [1]:

```
[Ввод пароля] ➔ [PBKDF2 + Соль] ➔ [Ключ шифрования AES-256-GCM] (Остается в ОЗУ)
                                         │
[Encrypted Session от VPS] ──────────────┴──────────────➔ [Расшифрованная IndexedDB]
```

1.  **Генерация ключа (KDF):** При вводе пароля на форме входа в браузере запускается алгоритм **PBKDF2** с солью [1]. Он генерирует 256-битный симметричный ключ шифрования `Derived_AES_Key` [1].
2.  **Загрузка данных:** После успешной JWT-авторизации фронтенд скачивает с сервера зашифрованный текстовый массив (blob) `encrypted_cookies` [1].
3.  **Дешифрация на клиенте:** С помощью `Derived_AES_Key` и алгоритма **AES-GCM-256** этот массив расшифровывается прямо в браузере и записывается в базу данных IndexedDB Scramjet [1].
4.  **Синхронизация сессии:** Каждые 5 минут или при закрытии вкладки фронтенд считывает куки из IndexedDB, шифрует их ключом `Derived_AES_Key` и отправляет зашифрованный пакет обратно на VPS [1].
5.  **Экстренное уничтожение данных (Panic Button):**
    *   При закрытии вкладки (`beforeunload` / `pagehide`), нажатии кнопки «Выход» или при неактивности пользователя более 15 минут запускается процедура очистки.
    *   Скрипт отправляет финальный зашифрованный бэкап на сервер, после чего полностью очищает `localStorage`, `IndexedDB` и память Pinia [1]. На компьютере колледжа не остается физически ни одного файла или куки вашей сессии [1].

## 2. Спецификация интерфейса виртуального браузера

Интерфейс представляет собой полноценную копию браузера внутри вкладки Vue 3 [1.2.6]:

```
+--------------------------------------------------------------+
| [ Вкладка 1 × ] [ Вкладка 2 × ] [ + ]                        |  <-- Панель вкладок
+--------------------------------------------------------------+
|  ←   →   ↻   [ https://2ip.ru                            ]  |  <-- Панель навигации (Адресная строка)
+--------------------------------------------------------------+
|                                                              |
|                                                              |
|                     [ Контент Сайта ]                        |  <-- frames-container (Scramjet frames)
|                                                              |
|                                                              |
+--------------------------------------------------------------+
```

### 2.1 Адресная строка с автодекодированием
Поскольку Scramjet кодирует URL-адреса с помощью алгоритмов XOR (для маскировки от DPI) [1.1.2], адрес в iframe выглядит нечитаемо (например, `/uv/service/hvtrs8%2F-dwcidwcigm...`).
*   **Решение:** Скрипт во Vue постоянно отслеживает событие смены адреса внутри активного фрейма, считывает его, пропускает через функцию `__uv$config.decodeUrl()` и выводит в адресную строку понятный человеческий адрес (`https://duckduckgo.com/`), чтобы пользователь мог скопировать его в один клик.

### 2.2 Чат-система (WebSockets)
В интерфейс встроена боковая панель (или вкладка) чата:
*   **Сквозное шифрование:** Перед отправкой сообщения в сокет текст шифруется на клиенте по стандарту **AES-GCM-256** с использованием общего группового ключа (или ключа, полученного при обмене Диффи-Хеллмана) [1]. На сервер сообщение уходит зашифрованным, расшифровать его в БД невозможно.
*   **Rate Limiting:** Redis на бэкенде отсекает отправку сообщений чаще, чем 1 сообщение в 2 секунды с одного аккаунта, предотвращая флуд.
