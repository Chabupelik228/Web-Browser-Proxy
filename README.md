# 🚀 Secure Browser

**Secure Browser** — это специализированный антидетект-браузер с гибридной архитектурой, разработанный для максимальной анонимности, безопасного туннелирования трафика и жесткого противодействия системам антифрода. 

Главная особенность проекта — режим **Camouflage (Маскировка)**. Браузер визуально и технически мимикрирует под стандартный Google Chrome, позволяя пользователю скрывать настоящую деятельность внутри изолированных "инкогнито"-сессий, трафик которых маршрутизируется через защищенный персональный WISP-туннель.

---

## 🎯 1. Концепция и решаемая проблема

### Проблема (Обход сетевых блокировок)
В корпоративных сетях, колледжах и публичных Wi-Fi часто используются жесткие файрволы (DPI), которые блокируют доступ к популярным ресурсам (соцсети, мессенджеры, видеохостинги) по SNI или IP. Обычные VPN-протоколы (OpenVPN, WireGuard) легко детектируются и блокируются провайдерами, а стандартные веб-прокси уязвимы к обнаружению.

### Решение
Secure Browser создан как ультимативный инструмент для обхода любых сетевых ограничений за счет инкапсуляции трафика:
1. **Пропуск трафика через "Белый домен":** Весь трафик браузера заворачивается и отправляется на один единственный разрешенный (или еще не попавший в категории файрвола) личный домен. 
2. **Инкапсуляция в WebSocket (WISP протокол):** Для сетевого оборудования провайдера/колледжа весь ваш серфинг выглядит как обычный обмен текстовыми/бинарными сообщениями по защищенному (TLS/HTTPS) WebSocket-каналу с одним безобидным сайтом.
3. **Глубокая маскировка (Camouflage):** В дополнение к обходу блокировок, браузер защищает от антифрод-систем (Cloudflare, Datadome), подменяя цифровые отпечатки и изолируя сессии на уровне движка WebView2.

## 🏗 2. Архитектура и сетевой стек

Архитектура проекта разделена на два независимых контура: **Desktop Client (Rust/Tauri + Vue)** и **Remote Backend (Node.js/Fastify)**.

### Схема прохождения трафика
`Desktop Client` ➔ `Local Loopback Proxy (Rust)` ➔ `Wisp over WebSocket (TLS)` ➔ `VPS Server (Node.js)` ➔ `Target Website`

1. **Local Loopback (Rust/Tokio):** Встроенный в браузер локальный прокси-сервер перехватывает все сетевые запросы WebView2.
2. **Wisp Tunneling:** Локальный прокси упаковывает сырые TCP/UDP пакеты в протокол Wisp и отправляет их через зашифрованный WebSocket-канал на бэкенд.
3. **Remote Execution:** VPS-сервер распаковывает Wisp-фреймы и выполняет запросы от своего имени (IP-адреса сервера), возвращая результат клиенту.

### Предотвращение сетевых утечек
- **WebRTC & DNS:** Полностью блокируются утечки реального IP-адреса. DNS-резолвинг происходит строго на стороне VPS.
- **QUIC / HTTP3:** Принудительно отключается для исключения UDP-утечек в обход туннеля.
- **Killswitch:** При разрыве Wisp-туннеля локальный Loopback-прокси немедленно сбрасывает все соединения, исключая возможность выхода в сеть с реального IP.

## 🕵️‍♂️ 3. Стелс и антифрод (Camouflage)

### Изоляция сессий и профилей
- **Нулевой контекст:** При переключении в скрытый режим запускается новая сессия WebView2 (In-Memory / InPrivate). Она не имеет доступа к куки, кэшу или TLS-сессиям "фейкового" браузера.
- **Clean Sockets:** При каждом переподключении очищаются данные просмотров, гарантируя отсутствие связи между сессиями (Zero-Leak).

### Спуфинг фингерпринта
- **Client Hints & User-Agent:** Браузер внедряет актуальные заголовки Chrome (`Sec-Ch-Ua`, `Sec-Ch-Ua-Mobile`) и подменяет `navigator.userAgentData` через инъекцию JS на этапе `DocumentCreated` (до срабатывания любых скриптов на сайте).
- **Вырезание автоматизации:** Аргумент `--disable-blink-features=AutomationControlled` исключает обнаружение свойства `navigator.webdriver`.

## 🛡 4. Безопасность и анти-абуз

Система авторизации спроектирована для защиты от кражи сессий, Replay-атак и использования браузера на чужих устройствах.

### Защита рукопожатия Wisp
WebSocket-рукопожатие защищено криптографически:
- **HMAC Signature:** Каждый запрос на создание туннеля подписывается алгоритмом `SHA256(JWT + Timestamp + Obfuscated_Salt)`.
- **Obfuscation (obfstr):** Секретная соль зашифрована на этапе компиляции Rust-бинарника и не видна при реверс-инжиниринге утилитой `strings`.
- **Anti-Replay Attack:** Бэкенд проверяет метку времени (`Timestamp`) с окном валидности в 30 секунд. Перехваченный пакет невозможно использовать повторно.
- **Timing Attacks:** Все хэши на сервере сравниваются через `crypto.timingSafeEqual`.

### Привязка к железу (Stateless Hardware Binding)
- Сервер генерирует токен с привязкой к уникальному аппаратному ID устройства.
- Во избежание утечки информации о железе при краже токена, в JWT записывается не сам ID, а его односторонний хэш: `HMAC-SHA256(deviceId, JWT_SECRET)`.
- При ротации токена клиент присылает свой ID, сервер хэширует его на лету и сверяет с хэшем из токена.
- **Single-Session Lock:** Redis следит за тем, чтобы под одним аккаунтом одновременно мог быть открыт только один активный Wisp-сокет.

### Жизненный цикл сессий
- Вход в систему осуществляется через **одноразовые OTP-пароли**, которые генерирует привязанный Telegram-бот.
- **Access Token:** Живет 15 минут, используется для авторизации Wisp-соединений.
- **Refresh Token:** Живет 30 дней, передается исключительно через безопасные `HttpOnly` куки, защищен от XSS.

## 💻 5. Стек технологий

- **Core & Tunneling:** Rust, Tauri v2, Tokio, Tungstenite (WebSocket), Byteorder.
- **Web Engine:** Microsoft Edge WebView2.
- **Frontend (UI):** Vue 3, Vite, Pinia (State Management), Tailwind CSS / Vanilla CSS.
- **Backend:** Node.js, Fastify, Wisp-JS, Argon2 (хэширование паролей), JWT.
- **Databases:** PostgreSQL (пользователи), Redis (OTP, Single-Session Lock).
- **Bots:** Telegraf / Python Telebot (OTP-коды).

## ⚙️ 6. Запуск и сборка

### Требования
- **Для клиента:** Windows 10/11, Rust Toolchain, Node.js 18+, WebView2 Runtime.
- **Для сервера:** Linux VPS, Docker & Docker Compose, Node.js 18+.

### Настройка окружения
1. Настройте бэкенд, скопировав шаблон:
   ```bash
   cp backend/.env.example backend/.env
   # Укажите POSTGRES_URL, REDIS_URL, JWT_SECRET, BOT_TOKEN и WISP_SALT
   ```
2. Настройте фронтенд для сборки:
   ```bash
   cp frontend/.env.example frontend/.env
   # Укажите VITE_API_DOMAIN и WISP_SALT (соль должна совпадать с бэкендом)
   ```

### Запуск в режиме разработки (Dev)
```bash
# Бэкенд
cd backend
npm install
npm run dev

# Фронтенд (браузер)
cd frontend
npm install
npm run tauri dev
```

### Релизный билд (Production)
Сборка изолированного бинарника браузера со вшитой криптографией:
```bash
cd frontend
npm run tauri build
```
Готовый `.exe` файл будет находиться в директории `frontend/src-tauri/target/release/`.
