# 🚀 Secure Browser — Isolated Browser & Secure Tunneling Platform

**Secure Browser** — это клиент-серверная платформа с гибридной архитектурой, разработанная для обеспечения максимальной изоляции сессий, безопасного туннелирования трафика и централизованного управления клиентами.

Ключевая особенность проекта — использование изолированных in-memory профилей на базе WebView2, трафик которых жестко маршрутизируется через защищенный WebSocket-туннель (WISP) с привязкой к аппаратному идентификатору устройства. Платформа также включает возможности удаленного мониторинга и управления сессиями.

---

## 🎯 1. Архитектура и концепция

Проект решает задачи безопасной работы в сетях с недоверенной инфраструктурой или строгими политиками доступа, обеспечивая защиту корпоративного или личного трафика:

1. **Безопасное туннелирование:** Весь трафик браузера прозрачно инкапсулируется в зашифрованный WebSocket-канал (WISP). Для DPI и сетевого оборудования это выглядит как стандартный обмен данными по HTTPS с обычным сервисом.
2. **Изоляция браузерных профилей:** В отличие от обычных браузеров, клиент использует эфемерные WebView2-сессии, гарантируя отсутствие утечек состояния между сессиями (cookie, кэш, local storage).
3. **Fail-safe Networking & Скрытый режим:** Платформа имеет встроенный резервный механизм — "Дежурный браузер" (Decoy), позволяющий осуществлять обычный веб-серфинг. Переход в режим защищенного туннелирования возможен только через авторизацию по уникальному протоколу, что защищает клиента от несанкционированного использования.

## 🏗 2. Архитектура и сетевой стек

Архитектура проекта разделена на два независимых контура: **Desktop Client (Rust/Tauri + Vue)** и **Remote Backend (Node.js/Fastify)**.

### Схема прохождения трафика
`Desktop Client` ➔ `Local Loopback Proxy (Rust)` ➔ `Wisp over WebSocket (TLS)` ➔ `VPS Server (Node.js)` ➔ `Target Website`

1. **Local Loopback (Rust/Tokio):** Встроенный в браузер локальный прокси-сервер перехватывает все сетевые запросы WebView2.
2. **Wisp Tunneling:** Локальный прокси упаковывает сырые TCP/UDP пакеты в протокол Wisp и отправляет их через зашифрованный WebSocket-канал на бэкенд.
3. **Remote Execution:** VPS-сервер распаковывает Wisp-фреймы и выполняет запросы от своего имени (IP-адреса сервера), возвращая результат клиенту.

### Предотвращение сетевых утечек
- **WebRTC & DNS:** Полностью блокируются утечки реального IP-адреса. DNS-резолвинг происходит строго на стороне VPS.
- **QUIC / HTTP3:** Принудительно отключается для исключения UDP-утечек в обход туннеля.
- **Killswitch:** При разрыве Wisp-туннеля локальный Loopback-прокси немедленно сбрасывает все соединения, исключая возможность выхода в сеть с реального IP.

### Load Balancing & Отказоустойчивость (Domain Distribution)
Бэкенд динамически распределяет WISP-сессии по пулу endpoint'ов (например, `stream.*`, `assets.*`, `edge.*`) для равномерного распределения нагрузки и повышения отказоустойчивости инфраструктуры.
- Сервер автоматически маршрутизирует каждое новое подключение на наименее загруженный узел.

## 🕵️‍♂️ 3. Изоляция сессий и управление состоянием

### Жизненный цикл эфемерных сессий
- **Нулевой контекст:** При переключении в туннелируемый режим запускается полностью изолированная сессия WebView2 (In-Memory / InPrivate).
- **Stateless Cleanup:** Rust-ядро выполняет агрессивную очистку кэша, локального профиля (`com.google.chrome`) и временных файлов при любом переходе между режимами или закрытии приложения. Такой подход минимизирует сохранение локального состояния защищенных сессий на жестком диске.

### Управление профилем (Fingerprint Management)
- **Нормализация заголовков:** Браузер переопределяет Client Hints (`Sec-Ch-Ua`, `Sec-Ch-Ua-Mobile`) и подменяет свойства объекта `navigator` через инъекцию JavaScript на этапе `DocumentCreated` для стандартизации отпечатка браузера.
- Флаг `--disable-blink-features=AutomationControlled` отключает стандартные индикаторы автоматизации WebView.

## 🛡 4. Безопасность и анти-абуз

Система авторизации спроектирована для защиты от кражи сессий, Replay-атак и использования браузера на чужих устройствах.

### Защита WISP-Туннеля (Payload Encryption & Handshake)
- **AES-GCM Encryption:** Весь трафик внутри WebSocket-туннеля WISP дополнительно шифруется на уровне приложения с помощью **AES-256-GCM** (помимо стандартного TLS). Ключ шифрования вычисляется на базе распределенной секретной соли.
- **HMAC Signature & Defense-in-Depth:** Каждый запрос на создание туннеля подписывается алгоритмом `SHA256(JWT + Timestamp + Obfuscated_Salt)`. Секретная соль подвергается статической обфускации через макрос `obfstr` на этапе компиляции Rust-клиента. Поскольку секрет встроен в клиент, он по умолчанию рассматривается как потенциально компрометируемый, поэтому архитектура **не полагается на его конфиденциальность как на единственный механизм безопасности** (реализована защита от replay-атак и жесткая привязка к JWT).
- **Anti-Replay Attack:** Бэкенд проверяет метку времени (`Timestamp`) с окном валидности в 30 секунд.
- **Timing Attacks:** Сравнение хэшей на сервере выполняется за константное время через `crypto.timingSafeEqual`.

### Device-Bound Authentication
- Сервер генерирует токен с привязкой к уникальному аппаратному ID (HWID) устройства.
- Во избежание утечки информации о железе при краже токена, в JWT записывается не сам ID, а его односторонний хэш: `HMAC-SHA256(deviceId, JWT_SECRET)`.
- **Single-Session Enforcement:** Redis следит за тем, чтобы под одним аккаунтом был активен только один HWID. При входе с другого устройства старое устройство немедленно деавторизуется, а его WISP-сокеты принудительно обрываются.

### Централизованное управление клиентами (Remote Control)
Через защищенное Server-Sent Events (SSE) соединение бэкенд может удаленно управлять подключенными клиентами:
- Канал управления изолирован, доступен только по валидному JWT токену и зашифрован базовым TLS.
- **Remote Termination (del):** Удаленное принудительное завершение процесса клиента и сброс его локального состояния (выполняется администратором сервера).
- **Session Revocation (norm):** Принудительный сброс активной сессии пользователя на устройстве.
- **Find Device:** Механизм визуальной идентификации активных клиентов с помощью скрытых виджетов.

### Административная панель (Telegram Bot)
Управление инфраструктурой вынесено в удобного Telegram-бота с панелью администратора:
- **Белые списки:** Поддержка Whitelist для IP-адресов серверов и Telegram-аккаунтов, имеющих право генерировать OTP коды.
- **Удаленные логи:** Централизованный сбор логов входов и закрытий (Device Events) в базу данных без локального хранения, с поиском по логину и HWID прямо из бота.
- **Статистика трафика:** Отслеживание и подсчет использованного трафика WISP-сессий в реальном времени.

### Жизненный цикл сессий
- Вход в систему осуществляется через одноразовые **OTP-пароли**, которые генерирует Telegram-бот.
- **Access Token:** Живет 15 минут, используется для авторизации Wisp-соединений.
- **Refresh Token:** Живет 30 дней. Для максимальной гибкости интеграции поддерживается передача токена обновления как через тело запроса (JSON), так и через защищенные `HttpOnly` cookie.

## 💻 5. Стек технологий

- **Core & Tunneling:** Rust, Tauri v2, Tokio, Tungstenite (WebSocket), Byteorder.
- **Web Engine:** Microsoft Edge WebView2.
- **Frontend (UI):** Vue 3, Vite, Pinia (State Management), Tailwind CSS / Vanilla CSS.
- **Backend:** Node.js, Fastify, Wisp-JS, Argon2 (хэширование паролей)В, JWT.
- **Databases:** PostgreSQL (пользователи), Redis (OTP, Single-Session Lock).
- **Bots:** Telegraf / Python Telebot (OTP-коды).

## ⚙️ 6. Запуск и сборка

### Требования
- **Для клиента:** Windows 10/11, Rust Toolchain, Node.js 18+, WebView2 Runtime.
- **Для сервера:** Linux VPS, Docker & Docker Compose, Node.js 18+.

### Настройка окружения
1. Настройте бэкенд, скопировав шаблон:
   ```bash
   cp backend/.env.example backend/.env
   # Укажите POSTGRES_URL, REDIS_URL, JWT_SECRET, BOT_TOKEN и WISP_SALT
   ```
2. Настройте фронтенд для сборки:
   ```bash
   cp frontend/.env.example frontend/.env
   # Укажите VITE_API_DOMAIN и WISP_SALT (соль должна совпадать с бэкендом)
   ```

### Запуск в режиме разработки (Dev)
```bash
# Бэкенд
cd backend
npm install
npm run dev

# Фронтенд (браузер)
cd frontend
npm install
npm run tauri dev
```

### Релизный билд (Production)
Сборка изолированного бинарника браузера со вшитой криптографией:
```bash
cd frontend
npm run tauri build
```
Готовый `.exe` файл будет находиться в директории `frontend/src-tauri/target/release/`.
